JPH-3: Epic | To Do | Grant × Program × GL Allocation Tool — MVP
DESC:
 Problem
Nonprofit CPAs are repeatedly asked "how much of Grant X maps to Program Y, broken down by GL expense category?" QuickBooks Online allows effectively one classification per transaction, so the same dollar can't be simultaneously "Salaries & Wages" (GL/accounting view) and "Culinary Training Personnel" (grant-budget view). Today every request is a 1–2 hour one-off spreadsheet rebuild.
Goal
A server-rendered web app that ingests QuickBooks-shaped accounting data, lets the user define grants, programs, grant budget lines, and a crosswalk from grant budget lines to GL accounts/classes, applies shared-cost allocation rules, and regenerates grant × program × GL reports, budget-vs-actual, restricted-fund balances, and AI-drafted funder narratives on demand.
Approach
Phase 1 (bulk of MVP): no live QuickBooks. All data enters through a pluggable DataSource interface with a CSV adapter and a realistic dummy dataset.

Phase 2: live QuickBooks Online adapter implementing the same interface.

Architectural constraints (apply to every story)
Not a single-page app. Next.js App Router, server components by default, real URL per page, server actions for mutations, forms work without client JS. Client components only for small interactive islands (allocation split editor, report filters). No client-side global state library, no client-side router-driven "app shell".

TypeScript strict mode end to end.

Postgres + Prisma. All money stored as integer cents (BigInt/Int), never floats. All allocation math uses integer cents with a deterministic remainder rule (largest-remainder, ties to lowest ID).

QuickBooks is the source of truth for transactions; the app never mutates source transactions. Allocations/mappings are an overlay with a full audit trail back to source line IDs.

Single organization per deployment is acceptable for MVP, but every table carries orgId so multi-tenant is additive later.

Tests: Vitest for unit/domain, Playwright for page flows. The dummy dataset (see test-data story) has hand-computed expected totals that tests assert against.

Out of scope for MVP
Multi-tenant CPA portal, write-back to QuickBooks, billing, QuickBooks Desktop.
Definition of done (epic)
Using only the dummy CSVs, a user can import data, configure grants/programs/crosswalk/allocation rules, and produce a crosstab report, a budget-vs-actual report, and a restricted-fund balance view that match the documented expected totals, plus export them and generate a draft funder narrative. The live QBO adapter can pull a QBO sandbox company into the same pipeline.

== JPH-5 [Story] [To Do] parent=JPH-3 :: 02 · Domain data model: source ledger mirror + grant/program/crosswalk/allocation overlay
Story
As the developer, I want a Prisma schema that cleanly separates (a) a read-only mirror of QuickBooks-shaped source data from (b) the user-defined grant/program/allocation overlay, so the app never mutates source data and every derived number traces back to a source line.
Layer A — Source mirror (populated only by DataSource adapters)
All rows carry orgId, sourceSystem (csv | qbo), externalId (the source system's ID), importBatchId, importedAt. Unique on (orgId, sourceSystem, externalId).
Account — chart of accounts. number, name, type (Income/Expense/Asset/Liability/Equity/COGS/OtherExpense/OtherIncome), detailType, parentExternalId, active.

TrackingClass — QBO Class. name, parentExternalId, active.

TrackingLocation — QBO Location/Department. name, active.

Party — QBO Customer/Project/Vendor/Employee unified. kind (customer | project | vendor | employee), displayName, parentExternalId (projects/sub-customers).

Transaction — header. txnType (Bill, Expense, Check, JournalEntry, Deposit, Invoice, SalesReceipt, Payroll, CreditCardCredit, VendorCredit), txnDate, docNumber, memo, partyId?, totalCents.

TransactionLine — the atomic unit everything else references. transactionId, lineNumber, accountId, classId?, locationId?, partyId? (line-level customer/project), description, amountCents (signed: expenses positive debit, income positive credit — document convention precisely), postingType (debit | credit).

Layer B — Overlay (user-defined, editable, versioned)
Program — name, code, description, functionalCategory (program | management_general | fundraising), active, optional matchClassIds[] (classes that map to this program by default).

Grant — name, funder, awardNumber, startDate, endDate, awardAmountCents, restrictionType (purpose | time | both | unrestricted), status (draft | active | closed), revenueAccountId?, optional matchPartyIds[] / matchClassIds[].

GrantProgram — many-to-many with optional plannedShareBps (basis points).

GrantBudgetLine — the funder's budget categories. grantId, code, name (e.g. "Culinary Training Personnel"), budgetCents, programId?, sortOrder.

CrosswalkRule — maps source lines to a GrantBudgetLine. Matchers (all optional, AND-combined): accountIds[], accountRange (number from/to), classIds[], locationIds[], partyIds[], descriptionContains, dateFrom/dateTo. Target: grantBudgetLineId. priority (lower wins), active.

AllocationRule — splits a matched pool of lines across targets. See story 07 for semantics. name, matchers (same shape as CrosswalkRule), method (fixed_pct | ratio_of_driver), effectiveFrom/To, targets[] → AllocationTarget { programId?, grantBudgetLineId?, shareBps }.

AllocatedLine — materialized output: sourceLineId, allocationRuleId?, crosswalkRuleId?, programId?, grantId?, grantBudgetLineId?, amountCents, computeRunId. Sum of AllocatedLine.amountCents per sourceLineId must equal the source line amount exactly (invariant).

ComputeRun — each recompute: startedAt, finishedAt, configHash, sourceBatchIds[], status, warnings JSON.

AuditEvent — every overlay create/update/delete: entity, entityId, before JSON, after JSON, actor, at.

ImportBatch — see story 03.

Narrative — see story 10.

Acceptance criteria
Prisma schema + migration committed; ERD (Mermaid) in docs/data-model.md.

Money columns are integer cents. Percentages are integer basis points (10000 = 100%).

A domain-level invariant checker assertAllocationBalanced(runId) exists and is covered by tests.

Overlay tables never have FK cascades that delete source rows; deleting an import batch is blocked if a closed ComputeRun references it.

== JPH-9 [Story] [To Do] parent=JPH-3 :: 06 · Crosswalk: map grant budget lines ↔ programs ↔ GL accounts (with coverage & conflict checks)
Story
As a CPA, I want to declare once that e.g. "Culinary Training Personnel" = program CT × accounts {6010, 6020}, so the same source dollar keeps its GL identity ("Salaries & Wages") while also counting toward the funder's budget line — without re-tagging anything in QuickBooks.
Model changes (amends story 02)
CrosswalkRule gains programIds[] as a matcher. Crosswalk is evaluated after allocation (story 07) against each AllocatedLine, so matchers see the allocated program, not only the source class. Matchers: programIds[], accountIds[], accountRange, classIds[], partyIds[], descriptionContains, dateFrom/dateTo (AND across fields, OR within a list). Target: one grantBudgetLineId. priority integer; lowest wins.
Resolution semantics
For each AllocatedLine, find active rules whose matchers all pass and whose grant period contains the line date.

If none → line is "unmapped" (not an error; reported in the coverage view).

If multiple → lowest priority wins; if tied → conflict (the line is flagged, excluded from grant totals, and listed on /crosswalk/conflicts). Never silently pick.

A line maps to at most one budget line (no double-counting across grants in MVP). Splitting one expense across two grants is done with an allocation rule (story 07) targeting budget lines directly.

Pages
